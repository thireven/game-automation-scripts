# Source map

The long half of `CODEMAP.md`: one row per `src/` file, the skills table, the
tooling under `tools/`, and what a change has to touch before it is finished.
`CODEMAP.md` is the index and is read whole; this file is not — **grep the file
name or the heading and read that row**. Paths are relative to `app.gap.Tsum/`.
A row is one clause: the reasoning behind it is the header comment of the file
it names. `npm run map:check` verifies both files against the tree.

## Source map — `src/`

In bundle order (the `files` list in `tsconfig.json`). One clause per file, so
this stays one read: **the long form is each file's own header comment**, which
is where a decision and its reasoning are kept together. For a name rather than
a file, see `CODEMAP.md` § Where a name lives.

| `src/appLifecycle.ts` | The game app: whether it is in front (the host's `foregroundApp`, else its own parse of every `dumpsys window` focus line when the host misreads a multi-display dump), which of its two builds this device plays (`gameBuild`: the Game Region setting, else in front, else last seen, else installed via `pm path`), getting it there (`startApp` skips the boot phase when the game's process is still alive: that is a resume, which comes back on the pause menu), and the two waits either side of a restart — which watch focus and the first fingerprint rather than a clock. | `src/board.ts` | Reading the board and drawing chains on it: `scanBoardQuick` (one capture, with the bubbles read off that same frame so a pop costs taps and no capture), `link`, and what the Bubble Strategy setting comes to — including the holds over it in a fever's last seconds and for two seconds after a skill activation, and `ripeGameBubbles`, which leaves a bubble that has just appeared, or has no tsums round it, for a later scan (All Bubbles ASAP skips it), and `popBubbleOverflow`, which stops the Mid Chain strategies hoarding a pile and is all of Save One. | `src/play.ts` | One round, start to finish. ## Skills — `src/skills/`

Each file registers itself with `registerSkill({types: [...]})` and is otherwise
a leaf: nothing outside `src/skills/` references its symbols. Adding one means a
new file here, a line in `tsconfig.json` after `skillCore.ts`, a `SkillType`
member in `src/shared.d.ts`, and a dropdown entry in `src/skillOptions.ts` —
under the group its activation belongs to, at its name, with the `status` saying
how finished it is. A new skill is almost always `SkillStatus.Alpha`, which lists
it on Alpha builds only; promoting it later is a one-word edit.

The Note below says only what makes a skill unlike the others — **how one works

## Adding something — what a change has to touch

The tables above say where things *are*; this one says what is not finished
until it is done, in order. Almost every row fails **silently**: a file the
bundle never loads, a method the compiler cannot see, a screen no frame ever
tests, a generated document that is now a lie. `DEVELOPMENT.md` § Where to start
is the same knowledge indexed by symptom instead. Where "Then run" names a
`pages:*` command, that is the development toolkit (`DEVELOPMENT.md` § The
development toolkit), run against this repo's build.

| Adding | Touch, in this order | Then run |

Four rules the tables cannot carry:

- **Which band a subscription joins is a contract, not a preference.**
  `observe` promises to take no captures and tap nothing; `record` is for
  measurements that need an untouched screen, captures included; `guard`,
  `dismiss` and `navigate` may tap; `notify` decides nothing. A handler that
  captures belongs in `record` — which is where the fever reading is, and why —
  and reads the look's own frame (`gPages.untouchedFrame()`) when it is there.
  Nothing checks this, and `PAGE_DISPATCH.md` will happily document the wrong
  choice.
- **Bubble taps go through the Bubble Strategy setting, or they are an
  override that says so.** Bubbles are worth more popped inside a chain than
  popped alone, so the play loop hoards them: `popGameBubbles` spends only what
  `bubbleTapBudget` allows, and the pile-up blind sweep runs under one strategy
  only — and not even then while a skill's claim stands, since a blind sweep
  cannot respect one. Two deliberate exceptions, and both say so in `registerSkill`:
  `sweepsBubbles` + `clearAllBubbles`, for skills that turn tsums *into* bubbles
  and so have no chain to save them for; and `claimsBubbles`, for a skill that
  makes the chain itself, where the strategy's own pop is a link taken out of it
  (`bubbleTapBudget` returns 0 while the claim stands, and what the skill still
  wants spent it asks for per chain through `popBubblesAfterChain`). The overflow pop
  (`popBubbleOverflow`) is part of every strategy but All Bubbles ASAP, not an
  exception: past `overflowAt` bubbles the Mid Chain ones keep only the richest
  `overflowKeep`, and Save One always keeps just one (Save One Mid Chain does
  the same as its chain pop). A new tap on a bubble that reads none of these silently
  undoes the setting.
- **A mode of a screen is not a page, and must not be read as one.** `variant`
  is documentation and tooling *by contract* (`PageDef` in `src/globals.d.ts`) —
  the script only ever learns the page name — so state like "a fever is running"
  is read from its own probe table (`ts.isFeverTime`), never from the matched
  key. Declaring the entry anyway is usually worth it: it gives the corpus
  configuration something to be tested against. Make it the plain entry's probes
  *plus* the new ones, because `betterPageMatch` ranks on probe count first and a
  shorter entry can never win.
  **Usually, not always** — a mode too small to survive the capture path cannot
  have an entry at all, and must not be given a `variant` either, because a
  configuration nothing fingerprints reads as a missing entry for ever.
  Formal Beast's twin gauge is the case: its channel is ~20 logical px thick,
  three pixels on the 360px-wide capture page probes are read from, so it is
  read at native resolution off a crop instead (`Tsum.readFormalBeastGauges`) and
  its three corpus frames are plain `GamePlaying`. The rule for deciding is the
  studio's probe sweep: if nothing usable separates the mode from the page's
  other frames, there is no entry to write.
- **Detection claims are cheap to prove, so prove them.** The detection suite
  runs production detection over its corpus, and against `dist/index.js` over
  what actually ships. Anything beyond page matching — a watcher, a state
  machine, a new `Tsum` method — can be driven the same way: `createRuntime` and
  `createTsum` from `tools/runtime/load.js` give you the real bundle over a real
  frame in a few lines.

Finish with `map:check`, `pages:docs` (or a build), and a `CHANGELOG.md` entry
under the section for the version
in `package.json` — plus a one-line `### Summary` bullet there if a player would
notice the change.
